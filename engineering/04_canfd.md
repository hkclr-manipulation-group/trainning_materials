## 1. 从CAN过渡：变化了什么

CAN总线让多个节点共享一对差分线；发送竞争通过仲裁解决。仲裁段仍需全网兼容的位时序。应用要另外定义节点、命令、反馈和单位。

| 概念 | 怎么理解 | 配置时影响什么 |
|---|---|---|
| CAN FD | 支持更长载荷和可选数据段速率切换的帧格式 | 控制器、收发器、驱动API和对端都要匹配 |
| 仲裁速率 / nominal bitrate | 多节点竞争总线时使用的速率 | 全部参与节点必须能正确同步和仲裁 |
| 数据速率 / data bitrate | 切换后数据阶段使用的速率 | 线束、拓扑和收发器带宽成为限制 |
| BRS | Bit Rate Switch，是否使用速率切换 | FD帧可以不切换；设置了数据速率不证明每帧用了它 |
| FDF | 标识FD帧格式 | 不能用“数据超过8字节”代替帧类型标志 |
| DLC | 数据长度代码 | 代码与实际字节数不是始终相等 |
| ESI（CAN FD） | Error State Indicator，发送节点错误状态指示 | 与EtherCAT的ESI描述文件完全不同 |
| ISO/non-ISO FD | FD协议实现版本差异 | 老硬件与新设备混用时要核对兼容模式 |

经典CAN的数据帧最多8字节，FD最多64字节；FD仍有11位/29位标识符，FD不使用经典远程帧请求机制。旧经典CAN节点不一定能容忍FD帧，不能只因接头相同就混接。协议结构与BRS背景参见[CiA CAN FD说明](https://www.can-cia.org/can-knowledge/can-fd-the-basic-idea)。

## 2. 位速率不是填一个数字就结束

一个标称位时间可拆为同步段和若干时间段，控制器在指定采样点读值。**时间量子tq**是更细的时间单位；**采样点**是位时间里读取电平的位置；**SJW**限制重同步时可调整的宽度。不同SDK可能把寄存器值编码成“实际值减一”，不能直接用结构体里的数套公式。

学习时用抽象例子：控制器时钟80MHz，实际分频4，得到tq=50ns；一个位占20tq，则位长1μs、速率1Mbit/s。若采样发生在16tq，采样点80%。这只是计算练习；实际数据段、传播延迟补偿和采样点由设备能力与网络评估决定。

把仲裁速率、数据速率、两个采样点、ISO模式、终端、通道、帧类型和BRS放在同一配置记录里。先按型号手册建立已支持的组合，再通过抓包及错误计数验证。不能一边掉帧一边只提高数据速率。

## 3. 长度：把DLC、API长度、应用有效长度分开

| DLC代码 | 0–8 | 9 | 10 | 11 | 12 | 13 | 14 | 15 |
|---|---|---|---|---|---|---|---|---|
| 总线上数据字节数 | 与代码相等 | 12 | 16 | 20 | 24 | 32 | 48 | 64 |

例如应用要发9字节，它需要使用能承载12字节的FD帧，并按应用协议约定填充余下3字节；接收方不能把填充误当新字段。设备SDK可能自动填充，也可能要求合法长度；查接口说明并在接收端确认。该映射见[Bosch作者CAN FD原始论文](https://can-cia.org/fileadmin/cia/documents/proceedings/2012_hartwich.pdf)。Linux的`canfd_frame.len`表示字节数，并非DLC编码。参见[SocketCAN接口定义](https://docs.kernel.org/networking/can.html)。

运行`python labs/engineering_lab.py canfd`：先预测9、33和65字节请求的结果，再看输出。应分别得到承载12、48字节，以及长度非法；程序不会把65截断成64。

解析位置前先检查通道、ID、FD/扩展标志、长度和命令。保留原始帧；不要把任意64字节缓存都当成64字节有效反馈。整数符号、字节序、缩放与轴侧仍由电机协议定义，FD不会自动统一它们。

## 4. 团队两套适配器代码怎样读

以下是当前工作区源码观察，不是设备实测。源码路径相对工作区父目录；培训仓库单独使用时需取得对应项目。

| 文件 | 实际可见内容 | 需要继续核对的问题 |
|---|---|---|
| `cxt_canfd/cxt_canfd.c` | 初始化调用`ZCAN_SetAbitBaud(...,1000000)`、`ZCAN_SetDbitBaud(...,5000000)`，启用终端 | 是否适合本工位；SDK返回值；设备与通道句柄的有效期 |
| 同文件`cxt_canfd_send` | 清零帧结构，写ID/len/data后调用`ZCAN_TransmitFD` | 所用头文件中BRS标志怎样设置；当前发送函数未显式设置，须抓包确认 |
| `zlg_canfd/zlg_canfd.c` | 使用`aset/dset`位时序，发送结构显式设`fmt=1, sef=0, brs=1` | 该SDK的时序编码和标准帧限制，不能凭另一SDK参数推断速率 |
| `zlg_canfd_whj_motor/zlg_canfd_whj_motor.c` | 协议层准备命令，适配器交换，按响应ID分支解析 | 寄存器回复、伺服状态、扩展状态应分别验证；超时与重试是否满足周期 |

特别练习：WHJ交换函数含最多3次接收尝试，每次调用接收传入10ms超时，未匹配后还等待10ms。由源码可见，它可能远超1ms控制周期；实际耗时取决于SDK返回行为。写出该阻塞调用为何不能直接放入要求1kHz的硬周期，再用实际时间戳确认。这里不声称对该驱动做过性能测量。

## 5. 工具分两条路径，不强行套命令

**厂家SDK路径：** 使用与设备型号、操作系统和CPU架构匹配的库；先运行厂家设备枚举与只读示例，确认设备索引/通道和库版本。团队ZCAN/VCI接口不自动等于SocketCAN，`ip link`找不到`can0`也不能据此判断USB设备坏了。

**SocketCAN路径：** 仅在Linux驱动已把设备注册为CAN网络接口时使用。先只读检查：

```bash
ip -details -statistics link show can0
candump -h
cansend -h
```

以下是隔离工位的配置模板，执行前将速率替换为工位表中已确认的值；示例的1M/5M不是所有设备的默认配置。对正在运行的接口执行down会中断业务。

```bash
sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000 dbitrate 5000000 fd on
sudo ip link set can0 up
ip -details -statistics link show can0
candump -L can0
```

驱动不支持时应明确报错并核对能力，不反复强行启用。初始化参数依据[Linux CAN FD设备配置](https://docs.kernel.org/networking/can.html)。

只有学习发送语法时，使用**虚拟接口vcan0**。在安装can-utils、支持vcan且该接口尚不存在的Linux教学机上：

```bash
sudo modprobe vcan
sudo ip link add dev vcan0 type vcan
sudo ip link set vcan0 up
candump -L vcan0
```

另一个终端发送：

```bash
cansend vcan0 123##1000102030405060708090A0B
```

`##`表示FD格式，后面的`1`是flags（本例BRS），随后12字节为任意教学载荷。期望看到ID 123、FD/BRS和12字节。语法见[can-utils源码与工具](https://github.com/linux-can/can-utils)。虚拟收发不验证电气、仲裁、ACK或真实速率；该任意ID/载荷不能改为`can0`发送给电机。

## 6. 一路从单节点走到多节点

1. 完成接线卡，核对两端终端与参考连接；记录每个节点硬件/固件版本。
2. 设置通道和FD时序，只发送协议确认的状态读取。同时保存错误计数、接收帧类型、ID、时间和载荷。
3. 手算一条反馈，与官方工具和团队解码结果交叉核对；收到本机回环发送帧不能当作设备回复。
4. 建立“一个接收入口→按通道/ID/命令分发”的结构。多个电机线程争抢同一通道的接收函数，可能互相取走回复。
5. 明确周期状态流与请求回复的规则。无事务号的协议限制同类未完成请求数量；超时后迟到的旧回复不能自动对应新命令。
6. 加第二个节点时确认ID范围无冲突，逐个比较接收周期、最大反馈年龄和错误计数。再逐步增加到目标数量。
7. 验证异常输入、迟到帧、缺失帧与应用停止后的设备行为。恢复通信后从未使能/待确认状态重新建立有效反馈，不自动重放旧运动。

## 7. 容量预算与排错

假定6个轴各以1kHz发送一帧命令并接收一帧32字节反馈，且命令也为32字节，仅载荷为`6×1000×2×32×8=3.072Mbit/s`。在假定5Mbit/s数据速率下，仅数据字节就占614.4μs/1ms；仲裁、控制/CRC字段、填充、帧间隔、错误重发与驱动调度还会继续增加。因此剩下385.6μs只是乐观余量，不是已经可用的系统裕量。

| 现象 | 证据 | 优先定位 |
|---|---|---|
| 经典帧能通，FD不通 | FD/BRS与ISO设置、错误计数 | 对端能力、数据段时序、SDK帧标志 |
| 单节点正常，多节点超时 | 每类ID周期、仲裁等待、接收分发 | 总线预算、ID冲突、阻塞式逐轴等待 |
| 发送量上升但无有效回复 | 本机回环与真实RX区分 | 供电、ACK、过滤规则、应用命令 |
| 偶发错误或bus-off | 错误计数与负载/线缆状态相关性 | 终端、线束、数据段采样、节点异常 |
| 32字节后数据错位 | 实际长度、填充与解析边界 | DLC与len混用、结构体对齐、拷贝越界 |

**bus-off**表示控制器因错误管理退出参与总线的一种状态。记录发生原因及恢复策略；自动重启控制器不应自动恢复运动目标。

验收：提交双速率与标志配置、长度映射题、单节点原始/解析对照、多节点延迟分布与错误计数、异常恢复流程。回答“5Mbit/s为何不等于应用每秒可稳定发送5Mbit数据？”答案必须包含仲裁段、协议开销、竞争、重发和主机调度。

## 带练1：亲手设计并解码一条12字节反馈

先在内存中自定一个**教学协议**，用它练字段设计和解码；它不是RMD、WHJ或任何厂家指令，不能发到真实电机。反馈CAN ID约定为`0x280+节点号`，载荷如下：

| 字节偏移 | 长度 | 内容 | 类型与单位 |
|---|---|---|---|
| 0 | 1 | 固定标记0xD1 | uint8 |
| 1 | 1 | 节点号1–127 | uint8 |
| 2 | 2 | 序号 | uint16，小端，循环计数 |
| 4 | 4 | 输出位置 | int32，小端，毫弧度 |
| 8 | 2 | 输出速度 | int16，小端，毫弧度/秒 |
| 10 | 2 | 电流 | int16，小端，毫安 |

为什么位置4字节、速度2字节？这是本练习根据范围做的选择：int16最大32767，若单位毫弧度/秒，最大正速度32.767rad/s；int32的位置范围大得多。实际选字段长度必须从设备范围和分辨率推导，不照搬本例。

给定节点2、序号65535、位置−250mrad、速度100mrad/s、电流−500mA。负数采用固定位宽二进制补码：32位−250等于`2³²−250=0xFFFFFF06`，小端字节为`06 FF FF FF`；16位−500等于`0xFE0C`，小端为`0C FE`。完整帧为`D1 02 FF FF 06 FF FF FF 64 00 0C FE`，应解析为−0.25rad、0.1rad/s、−0.5A。

在[CAN FD带练Notebook](../notebooks/13_canfd_workshop.ipynb)中先运行打包和解包，再分别改一个输入。源码`workshop_lab.py`使用`struct.pack('<BBHihh',...)`：`<`明确小端、标准大小且无隐式对齐；B/H/i/h分别是8位无符号、16位无符号、32位有符号、16位有符号。这个字符串把上表转成可检查的接口，不依赖机器本地结构体布局。

接收验证顺序为：目标通道/ID→FD帧标志→载荷12字节→标记→载荷节点与路由一致→序号与时间→换算并发布。顺序重要：长度不足时先拒绝，不能先索引数据；ID属于节点2但载荷写节点3时，不能仅因能解出float就接受。

**练习与答案：** 将位置−250改为+250，位置字节应变为`FA 00 00 00`；将最后一字节删掉，应报长度错误；将0xD1改0xA1，应报标记错误；把电流40000mA强塞进int16，应拒绝而非悄悄截断。保存原始字节及每一步拒绝理由，才能检查“解析成功”是否真正可信。

## 带练2：统一接收、按节点分发，再处理重复和回绕

工位有两个节点，反馈ID分别0x281和0x282。若两个电机线程都直接调用同一个适配器的接收函数，线程1可能取走节点2的反馈；它认为ID不匹配就丢弃，线程2随后超时。总线上明明有回复，应用仍会报错。修复思路是一个通道由一个接收入口取帧，再按`(通道,ID)`分发给各节点，而非每个节点自己抢总线收件箱。

Notebook提供`FeedbackRouter`。每个节点保存最后接受的序号、接收时刻和数值。两个节点互不覆盖：节点1没有更新时应单独标旧，不能因为节点2持续更新就把“整条总线”标成全新。

普通“新序号大于旧序号”在65535→0回绕时会失败。教学规则使用`delta=(new-old)&0xFFFF`：delta=0是重复；0<delta<32768认为前进；其余视为旧或存在歧义。这依赖任意有效比较之间跨越不足半个序号空间。长时间离线、设备重启或会话改变后，不能拿旧序号继续比较，应重新建立会话与状态。

手算时间线：1.000s接受seq65535；1.010s接受seq0，差值为1，是新帧；1.020s再次收到seq0，拒绝重复且不刷新1.010s；1.030s收到seq65535，差值65535，视为旧帧。1.080s检查，最后有效接收年龄为70ms；若上限50ms就已经过期。数值相同但序号前进可以是有效静止反馈，不应把“位置没变”当作重复规则。

**自己做：** 在Notebook里重放上述四帧，加一个错误通道、一个错误节点和一条只有11字节的帧。逐条写预测结果，再运行核对。观察失效帧是否污染最后有效位置和时间。样例计算的是接收后年龄，不假装已知设备内部采样时刻。

## 带练3：把周期预算拆到可测的位置

假定控制要求1ms更新六轴。错误实现是按轴循环“发送请求→等待回复→下一轴”，即使每轴平均0.2ms，六轴串行已经需要1.2ms；若其中一轴等10ms超时，整个周期被拖住。只把总线数据速率从2M改到5M，不会自动消除应用里的串行等待。

先画时间轴：周期起点→准备六轴目标→排队发送→总线发送→设备执行/采样→接收入口→节点状态更新→控制读取快照。每段记录实际起止，确认设备是否支持批量目标、周期广播或同步触发。没有协议支持时，不能凭上位机把所有节点变成同步采样。

容量计算至少分三层。第一层是载荷下界，前文六轴双向32字节得到61.44%；第二层计入帧结构、仲裁段、填充与帧间隔，需要准确格式或分析仪统计；第三层计入USB、适配器队列、设备响应和操作系统调度。只有第三层的端到端记录能回答应用截止时间是否满足。

运行两个负载工况：仅状态读取；状态读取加有限运动，再叠加允许的诊断流量。比较每节点更新间隔、最大连续缺失、总线错误与主机排队时间。故障发生时记录哪个ID、哪个通道、哪一层开始变慢；不要仅报告一个平均“总线延迟”。

**练习与解析：** 在6轴预算中增加一条1kHz、64字节诊断帧，仅载荷多512kbit/s，占5Mbit/s的10.24%，合计载荷占比71.68%。这不等于还有28.32%可随意使用，因为前两类计算都没包含完整开销。提出一种改进，如降低非控制诊断频率，并说明它是否改变运动反馈时效。改进前后必须用同一任务测量。
