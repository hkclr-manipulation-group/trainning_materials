# 05｜EtherCAT：从发现从站到同步控制多轴

**本门连续带练：**[直接进入逐步案例、练习与解析](#worked-lessons)。对象映射与字节偏移→两套状态联合门禁→周期时间线。

[工程课程](../ENGINEERING_PATH.md) · 前置：[接口分层](03_interfaces.md)、[单轴工位](../PRACTICAL_PATH.md) · 后续：[控制与实时执行](07_control.md)

任务：把一台驱动器接入主站，确认身份与过程数据映射，解释总线与驱动状态，读位置，再逐步验证周期目标和多轴同步。课程给出IgH只读命令与TwinCAT操作路径；实际主站、驱动器和ESI版本必须在工位表中指定。

## 1. 先把网口、主站、从站分清

主站安排周期通信，从站按配置读取属于自己的输出并写回输入。常见EtherCAT过程数据直接使用Ethernet帧，不能用“ping通”作为通信验收。专用从站控制器负责帧处理；普通带网口的电机不自动成为EtherCAT从站。

```text
主站指定网口 → 驱动器1 IN → 驱动器1 OUT → 驱动器2 IN → …
每个设备的控制/动力供电与接地另按设备图纸连接
```

按设备标注的IN/OUT和允许拓扑布线，第一工位先只接一个从站。不要把办公交换机随意插入这条周期链路；分支使用主站/设备方案支持的EtherCAT连接设备。普通EtherCAT与EtherCAT P的供电方式不能混用。通用背景见[Beckhoff EtherCAT技术说明](https://www.beckhoff.com/en-en/products/i-o/ethercat/)。

## 2. 描述文件、邮箱和过程映像

| 词 | 它实际是什么 | 在调试中看哪里 |
|---|---|---|
| ESI | EtherCAT SubDevice Information，设备XML描述 | Vendor ID、Product Code、Revision、PDO、同步模式 |
| ENI | 由配置工具生成的网络配置描述 | 不是每个主站都必须直接加载；依主站工作流 |
| CoE | CANopen over EtherCAT，复用对象字典等应用机制 | 并不是把物理CAN线接到网口 |
| 对象字典 | 用index:subindex定位参数的数据表 | 字段类型、读写权限、单位、是否可PDO映射 |
| SDO | 通过邮箱访问对象的服务 | 身份、配置、诊断；不当成每轴每周期同步目标通道 |
| PDO | 周期交换的过程数据对象 | 字段顺序、位宽、方向和映射偏移 |
| 过程映像 | 主站内存里供应用读写的输入输出区域 | 不是任意C结构体强制转换就正确 |
| Sync Manager / FMMU | 管理数据通道与逻辑地址映射的机制 | 通常由主站配置，根据设备映射诊断 |

先认识这些词的职责，再查看[ETG实现指南](https://www.ethercat.org/download/documents/ETG2200_V3i2i2_G_R_EtherCATImplementationGuide.pdf)的应用层、邮箱和过程数据章节。不同从站未必支持CoE或相同驱动规范；下面CiA 402部分仅针对支持该规范的驱动器。

## 3. 从站发现：识别到的必须是你配置的

记录主站版本、网卡型号/MAC、指定端口、驱动器型号/固件、ESI来源和文件哈希。断电核对布线和供电，保持电机不会输出意外运动，再启动扫描。

**IgH路径：** 在已按相应版本手册安装和配置主站的Linux工位，先用帮助确认命令；以下只读，不执行状态强切或对象写入。

```bash
ethercat version
ethercat master
ethercat slaves -v
ethercat pdos -p 0
ethercat sdos -p 0
ethercat upload --help
```

`-p 0`是选择总线位置0，应替换为实际目标。清单应与实物数量、位置、身份匹配。若对象字典确认`0x1018:01`为32位Vendor ID，可只读核对：

```bash
ethercat upload -p 0 -t uint32 0x1018 1
```

权限、邮箱支持和对象存在性依实际主站与设备而定。不能读取时先诊断，不改成写命令。命令背景见[IgH 1.6手册第7章](https://docs.etherlab.org/ethercat/1.6/pdf/ethercat_doc.pdf)，本课程未在当前Windows环境运行这些Linux硬件命令。

**TwinCAT路径：** 在工程里选择正确目标系统与专用网口，安装匹配ESI后扫描I/O；核对从站身份和拓扑，查看Online状态、CoE对象和Process Data映射，导出工程与诊断记录。进入运行/激活配置可能改变输出，应在工位停止和目标初始化已准备好后进行；不要仅为了让图标变绿就直接使能NC轴。界面名称随版本变化，记录实际版本及操作截图。

## 4. PDO从字典变成几个字节

RxPDO/TxPDO以**从站视角**命名：RxPDO是从站接收（主站输出），TxPDO是从站发送（主站输入）。方向反过来会导致读写错误。

以支持CiA 402的驱动器教学映射为例：

| 方向 | 对象示例 | 类型/位宽 | 用途 |
|---|---|---|---|
| 主站→从站 | 0x6040:00 | uint16，16位 | Controlword，控制状态迁移 |
| 主站→从站 | 0x607A:00 | int32，32位 | Target position，目标位置 |
| 从站→主站 | 0x6041:00 | uint16，16位 | Statusword，当前状态标志 |
| 从站→主站 | 0x6064:00 | int32，32位 | Position actual value，实际位置 |

对象索引示例可对照[Beckhoff DS402过程数据](https://infosys.beckhoff.com/content/1033/ep7211/6889103243.html)。本表不是某台设备的完整默认映射；模式、速度、故障等可能要额外配置。固定PDO和可重映射PDO的操作不同，按ESI和设备手册处理。

假设输入仅紧密排列“16位状态字+32位位置”，无填充，总计6字节。收到`27 00 18 FC FF FF`，小端解码为状态字`0x0027`、有符号位置`-1000`。若按无符号数读，会得到4294966296；若C结构体在32位字段前插入对齐填充，读取位置也会错。用主站注册获得的offset/bit position或明确的字节解析，不猜内存布局。

运行`python labs/engineering_lab.py ethercat`手算并核对。把最后一字节删除，应拒绝而不是补零；把模拟WKC从期望值降为较小值，应把该周期数据标记为无效。

## 5. 总线状态和电机状态是两回事

EtherCAT状态机决定通信阶段：INIT初始化；PREOP可进行邮箱通信；SAFEOP通常允许输入过程数据、输出保持设备定义状态；OP允许正常过程数据通信。SAFEOP不是功能安全认证，也不意味着重力轴被机械锁住。说明见[Beckhoff EtherCAT状态机](https://infosys.beckhoff.com/content/1033/el6201/1036980875.html)。

CiA 402驱动状态机则描述驱动是否准备好、是否开关使能、是否存在故障。**总线OP不等于驱动Operation enabled**。模式请求与显示（常见对象0x6060和0x6061）也要区分。

教学状态链：Switch on disabled → Ready to switch on → Switched on → Operation enabled；故障有独立分支。用设备规定的状态位掩码判断，不能只比较整个状态字是否等于某个常量，因为其他诊断位也会变化。输出控制字前必须知道当前状态和条件；“循环写6、7、15”不是完整状态机。

驱动进入使能前先对齐当前位置目标、配置限制、确认模式与抱闸流程。故障复位前先记录故障并处理原因；复位成功后不要直接恢复旧轨迹。

## 6. 从状态通信走到同步运动

**CSP/CSV/CST**分别是周期同步位置、速度、力矩模式（设备支持范围另查）。CSP中主站按周期提供位置要求，驱动完成其内部控制；选CSP不会自动生成合理轨迹。**DC**是Distributed Clocks，用于同步从站时钟与事件；**Sync0**是设备支持的同步触发之一。

DC让多个设备按各自同步时钟执行采样/更新，不会消除主机计算超时。主站仍需在规定窗口送达下一周期数据。支持哪些同步模式、周期范围及相位配置由从站能力决定。参见[Beckhoff DC技术说明](https://www.beckhoff.com/en-en/products/i-o/ethercat/)和[IgH时钟API](https://docs.etherlab.org/ethercat/1.6/doxygen/group__ApplicationInterface.html)。

开发时把周期任务与非周期任务分开：

```text
启动阶段：身份核对 → SDO配置 → PDO注册 → 时钟/周期配置 → 激活通信
周期阶段：按绝对时间唤醒 → 收包/处理输入 → 检查数据有效性和状态
          → 计算有界目标 → 写过程映像 → 时钟维护/排队/发送 → 记录周期计数
非周期任务：界面、磁盘日志、参数查询、分析报告
```

具体API调用次序和时钟更新位置必须遵循所用主站示例。IgH中可重点阅读`ecrt_master_receive`、`ecrt_domain_process`、`ecrt_domain_queue`、`ecrt_master_send`与DC相关接口；这些名字不是SOEM/TwinCAT的通用API。

## 7. WKC、周期和数据新鲜度怎么验

**Working Counter，WKC**用于检查EtherCAT数据报是否按预期被处理。预期值来自命令类型和映射配置，不能简单取“从站数量”；不同主站的domain聚合也要按API解释。数值符合只说明相应通信处理条件成立，不证明单位、机械位置或每个传感器内部采样都是正确的。WcState是工具对有效性的封装，见[Beckhoff WcState说明](https://infosys.beckhoff.com/content/1033/b110_ethercat_optioninterface/1984417163.html)。

每周期至少记录应用序号、唤醒时间、收发完成时间、期望/实际WKC、从站AL状态/错误码、驱动状态字、目标/实际位置以及可用的DC诊断。WKC异常时不能把上一周期缓存更新成“新测量”。

假设周期1ms，接收处理120μs、控制250μs、发送准备120μs、允许保留200μs，账面只剩310μs用于其他延迟；一次磁盘写入阻塞2ms就跨过截止时间。运行`python labs/engineering_lab.py timing`查看“平均周期合适但仍有一次迟到”的合成日志。

## 8. 分阶段实施与排错

1. 身份和ESI通过：保存扫描清单，核对每个站的版本；相同名字不足以证明Revision兼容。
2. PREOP配置通过：读回必要参数和映射，保存SDO错误信息；不在未知型号上复制其他轴的启动列表。
3. SAFEOP输入通过：核对位置单位、字节顺序和数据有效性，保留未使能状态。
4. OP周期通过：先稳定通信和初始化输出，再按CiA 402及设备流程使能；确认周期、WKC与模式。
5. 单轴有限运动通过：沿单电机卡检查正反向、限值、停止；再增加第二轴，测相位与同时采样条件。
6. 中断/恢复通过：在可控工位测试应用停止更新后看门狗动作，恢复先回待确认状态。电源断开及制动行为单独按设备流程验证。

| 现象 | 应读取什么 | 下一步 |
|---|---|---|
| 扫不到从站 | 网口绑定、链路灯、供电、拓扑 | 检查实际网口与IN/OUT，先单站 |
| 卡PREOP/SAFEOP | AL status code、PDO/SM配置、看门狗 | 根据错误码检查映射长度与启动参数 |
| OP但轴不动 | 状态字、模式显示、目标、抱闸、故障 | 按驱动状态机定位，不反复强切OP |
| WKC偶发不足 | 哪段链路、CRC/丢帧、主站周期 | 区分物理链路和主机迟到 |
| 多轴轨迹不同步 | DC模式、周期、目标生成时刻 | 检查同步配置与各轴所用时间基准 |
| 数据看似正常却跳变 | offset、位宽、符号、单位与新鲜度 | 原始过程映像逐字节核对 |

验收包必须含ESI/主站工程版本、从站身份、输入输出映射、两套状态机记录、WKC与周期统计、单轴和多轴实测范围。解释“所有从站OP、WKC正确，为什么仍不能宣布位置控制验收通过？”答案还需包含驱动状态、模式、目标语义、反馈时效和实物误差。

## 带练1：把对象字典映射到过程映像，逐个偏移核对

假设一个教学驱动器允许映射控制字0x6040:00（16位）、目标位置0x607A:00（32位）、模式0x6060:00（8位）。从站接收这三项，所以它们属于RxPDO、主站输出。按表中顺序紧密排列时，偏移分别0、2、6字节，总长度7字节。反向反馈另有自己的TxPDO，不能与输出偏移混为一个数组。

映射条目常可用“对象索引16位、子索引8位、长度8位”编码。例如`0x60400010`表达0x6040:00、长度0x10=16位；`0x607A0020`表达0x607A:00、32位。它是映射描述，不是给电机的目标值。理解这层区别后，才读设备ESI里的Index/SubIndex/BitLen。

对于允许动态映射的设备，配置流程通常涉及先关闭相应映射/分配的有效项数，写各条目，恢复条目数和分配，再核对总位宽。设备可能不支持动态映射，或者只允许特定状态下修改，所以这里不提供可直接执行的通用SDO写入序列。课堂先在纸上检查映射，真机按对应ESI和手册的启动流程操作。

给定控制字0x000F、目标位置1000计数、模式8，教学输出字节为`0F 00 E8 03 00 00 08`。最后的8在支持相应CiA 402定义的驱动器中可表示CSP请求，但请求不等于模式已接受；仍需要读模式显示和设备条件。对象是否存在、是否支持该模式、单位和齿轮比都由设备确定。

在[EtherCAT带练Notebook](../notebooks/14_ethercat_workshop.ipynb)中先计算7字节输出布局，再解码前文6字节输入。故意在32位字段前插入两个填充字节，观察原来的解码规则如何失配。将字段顺序改成模式、控制字、位置后，旧偏移全部失效；版本记录必须包含映射，而不只是C代码版本。

**练习与答案：** 加一个16位实际电流反馈，原6字节输入变成8字节；若软件仍坚持长度6，应明确拒绝，不要静默丢掉新字段。若软件只按“长度至少6”接受，可能掩盖映射改版。先建立明确版本/映射契约，再决定是否允许兼容尾部字段。

## 带练2：让两套状态机共同决定下一步

我们在纸上模拟一条完整启动链，程序只输出“下一步建议”，不向设备写控制字。输入包括AL状态、驱动Statusword、反馈是否有效、模式是否确认、目标是否与当前位置对齐、是否收到显式开始请求。

情形A：AL=PREOP、驱动状态Switch on disabled。下一步应继续配置总线和邮箱参数，不能发送周期运动。情形B：AL=OP但模式没确认。下一步仍是等待/核对模式，不能把OP当成启动完成。情形C：AL=OP、数据有效、模式确认、目标对齐、用户已开始，此时才沿设备状态机推进。

对符合该教学CiA 402链的状态，常见控制字请求为：Switch on disabled时请求Shutdown（0x0006），Ready to switch on时请求Switch on（0x0007），Switched on时请求Enable operation（0x000F）。每次发出请求都等待新有效状态满足下一条件，不按固定sleep后盲发下一字。Controlword各位含义可对照[Beckhoff对象说明](https://infosys.beckhoff.com/content/1033/ax8xxx_object/18797956107.html)，具体轴的支持和附加条件仍以型号资料为准。

为什么不能直接比较整个状态字？设基础状态0x0027表示Operation enabled，设备又置了不影响状态识别的附加位，读到0x1227。若代码写`status==0x0027`就会误报。用规范定义的状态掩码识别主状态，再单独解析其他诊断位。Notebook会并排展示0x0027与0x1227。

故障分支要单独处理：读到Fault时保留故障码、当前目标、模式和时间，先诊断，不能在循环里每周期自动复位。若反馈WKC无效，旧状态字即使显示Operation enabled也不能用来推进状态机。开始请求撤销后，运行中的轴应进入已定义停止策略，不能因为目标值暂时没变就无期限继续。

**作业：** 依次输入OP/0x0040、OP/0x0021、OP/0x0023、OP/0x0027，再插入一次无效反馈。预测每步建议。解析分别为请求6、7、15、允许有界参考；无效反馈进入停止策略。这个决策表只示范门禁逻辑，实际停止、抱闸和故障复位还需设备专用状态。

## 带练3：按时发包、时钟同步和按时采样不是同一个指标

假设主站每1ms生成目标。轴1和轴2都能收到这一帧，但若分别在收到时立即采样，两者采样时刻仍可能因设备处理而不同。DC的作用之一是让设备利用同步时钟在约定相位触发事件，而不是完全依靠帧到达瞬间。是否支持这个工作方式以及配置项由设备决定。

将一周期画成：计划唤醒t_k→应用实际唤醒→输入处理→目标计算→发出帧→从站接收→约定Sync0事件。主机计算可以有一定抖动，只要数据在设备所需窗口前到达；若已经错过窗口，DC不会替主机补出丢失目标。因此要分别统计主机release误差、应用finish时间、帧/WKC结果和从站同步诊断。

教学日志五次实际开始为0、1.0、2.4、3.0、4.0ms，计算时间为0.3、0.4、0.8、0.4、0.3ms。平均开始间隔恰好1ms，第三次却在3.2ms才算完，超过该周期3.0ms截止时间0.2ms。运行Notebook画出每个周期计划区间和实际计算区间，把迟到条着色。

最后做多轴检查：一条应用轨迹用同一个t_k生成各轴目标；输入必须带有效性与时刻；一轴失联时整机怎样处理由系统级策略规定，不由另一个轴“还有数据”决定。WKC期望值应从当前数据报与映射得到，不能在增加一轴后随手把常数加1。

**练习与解析：** 所有WKC都符合，但电机动作仍落后一周期，首先核对目标所属周期、写过程映像的先后、设备采样/执行相位与状态时间。WKC验证数据报处理，不验证你把“下一周期目标”误写成“上一周期目标”这类语义错误。
