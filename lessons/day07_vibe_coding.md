# 第七天：vibe coding 与可验证的工程交付

目标：利用 AI 完成一个范围明确的改动，自己理解关键实现，并用证据完成交付。

## 1. AI 协作的工作循环

这里把 vibe coding 作为用自然语言快速描述需求、让 AI 辅助生成和迭代代码的方式。机器人项目中，要把这个过程接到工程验证上：需求 → 读取上下文 → 小改动 → 查看差异 → 运行实验 → 解释结果。

AI 能帮助梳理目录、解释调用关系、提出故障假设、生成测试和初版文档。但它可能猜错 API、单位、文件状态或运行结果。你需要指出可用的证据，而不是让它凭空“把项目修好”。

## 2. 一个可以执行的任务描述

使用 [任务模板](../templates/AI_TASK.md)。例如：

```text
目标：让本仓库教学协议解码器拒绝未知标记和错误长度。
上下文：labs/course_lab.py，payload 是自创的 8 字节格式。
约束：保留现有正确载荷的行为，不引入第三方库。
验收：固定十六进制向量正常解码；短包、长包、未知标记均失败。
请先读实现与测试，再修改，报告实际执行的命令和结果。
```

这是需求模板示例，当前课程解码器已包含上述检查。结业时应选择尚未实现的任务，例如加入基于日志的序号重复统计，不能把已有功能重新声称为新成果。

对于“球太大”，应描述外扩误差、覆盖要求、预算和特定姿态；对于“no reachable”，应给出模型、配置、报错位置和对照结果。不要把“让所有测试绿”当作行为定义，测试本身也可能有错。

## 3. 看什么才算评审

逐项检查接口输入、输出单位、异常路径、资源释放、共享状态、文件范围和配置兼容性。遇到新依赖，核对实际导入位置、版本约束和安装方法。对于数学改动，用手算或独立算法验证，不让测试只重复同一公式里的错误。

先看 `git diff --stat` 判断范围，再看 `git diff` 判断内容；用 `git status` 检查有没有误带输出和本地配置。不要把密钥、设备凭证或未经允许的数据放入提示词和提交。

程序打印“成功”只证明执行到了那个分支。交付时区分：输入校验通过、CPU 单元测试通过、仿真通过、GPU 求解通过、真机验收通过。没有运行的环节写清楚。

## 4. 完成结业项目

按 [CAPSTONE.md](../assessments/CAPSTONE.md) 提交一个离线机器人诊断小工具。至少包括一个无效输入、一个正常输入、一条清晰错误信息和一份可复现报告。保留首次失败和修复后的证据，并讲清 AI 做了什么、自己核对了什么。

演示安排：2 分钟需求和系统图，3 分钟正常输入，2 分钟故障输入，2 分钟测试和限制，1 分钟答疑。对方应能在另一目录运行，而不用复制整个机器人资源库。

## 5. 后续四周

第 2 周深入机械与驱动选型、CAD 公差和 URDF 验证；第 3 周做协议联调、时序和闭环控制；第 4 周做轨迹、碰撞、标定和数据采集；第 5 周再进行策略训练、仿真评估与受控硬件验证。按岗位选择主线，保留跨层排错能力。
